== VM operations

=== Status

Status is collected tell-only: Root asks every twin and gathers answers for 5 s. A twin that has not answered by then shows as `Unknown`; a late answer is dropped. A quarantined VM has no twin and shows as `Quarantined { reason }` (a `VmCondition` variant), taken from its `quarantine/<name>` stream.

=== Stop

* `Stop` on a `Starting` VM cancels the start; the operation that started it ends with `vm.stopped_while_starting`.
* `Stop` on a `Failed` VM takes down the leftovers its failed start recorded.
* LocalQemu stops a machine in three steps: QMP `system_powerdown`, then `SIGTERM` after 30 s, then `SIGKILL` after 10 s more. Each signal goes only to a process whose identity is verified.

=== Start

* The boot timeout is fixed at 120 s.
* The Builder runs before GuestVm (0002); a `nix build` still running when the runtime stops is left to finish. It is idempotent, and the next start uses its result.
* The guest `term` file is always removed: no terminal is attached to a VM (0002, console).

=== Quarantine

0002's quarantine is implemented as follows:

* A twin that becomes `Unrecoverable` reports `VmReport::Unrecoverable { reason }` to Root. Root marks the VM quarantined in memory at once; the twin stays alive refusing commands, and Root routes nothing to it from then on.
* Root is not a persistent actor. It replays `quarantine/<name>` first: a live event means the VM is already recorded. Otherwise it appends `Quarantined { reason }` after the stream's last position (position 1 unless an earlier record was retired by `vacuum_vm`) through a plain `JournalMessage::Persist`; the journal's answers reach it as `RootMessage::Journal`. Root is the only writer, so a conflict means already recorded and is not an error. A store failure leaves the quarantine in memory only, logged.
* At start Root lists `quarantine/*` and `vm/*`, and replays every listed quarantine stream for its reason. Requests are held until both listings and every reason are in; then a twin is spawned for every `vm/*` name that is not quarantined. A record that can't be read counts as quarantined: its twin would otherwise replay a stream that may be broken.
* `start` and `stop` on a quarantined VM are refused (`runtime.vm.quarantined`, hint: `amoeboid vacuum_vm NAME`); `status` shows `Quarantined { reason }` without asking any twin.
* Envelope: `{"version": 1, "event": {"quarantined": {"reason": Report}}}`, the persistent actors' envelope.

=== Vacuum

`amoeboid vacuum_vm NAME` removes everything a VM owns: it stops the VM (reaping its verified processes), removes its runtime directory and state directory, and retires its streams (`vm/<name>`, `quarantine/<name>`). It works on quarantined VMs, which have no twin to stop them.

Root runs it as one operation (`VmRequest::Vacuum`, answered `VmReply::Vacuumed`):

----
Vacuum ─▶ [twin, not quarantined] VmCommand::Stop ─▶ Stopped ─┐   (stop failed: vacuum fails, twin keeps running)
       └▶ [quarantined] ───────────────────────────────────────┴▶ stop the twin actor
          ─▶ vacuum task: TERM every process carrying the VM's nonce, KILL survivors after 10 s,
             remove runtime and state directories ─▶ RootMessage::Vacuumed
          ─▶ Retire vm/<name> ─▶ Retire quarantine/<name> ─▶ VmReply::Vacuumed
----

* Graceful first: a twin that can run stops the VM through its own path (QMP, then signals) and records it; the task only ends what is left.
* The task needs no history: a VM's processes are found by the environment entry `AMOEBOID_NONCE=<name>/` (VM names hold no `/`, so no other VM's nonce shares the prefix). The nonce is the runtime's mark, so a match is a process the runtime spawned for that VM; each is signalled through a verified pidfd. A zombie counts as gone.
* The task is not an actor: it runs no conversation, only effects, and tells Root its result.
* `quarantine/<name>` is retired last, so a vacuum interrupted halfway leaves the VM quarantined and vacuumable again.
* Only names Root knows (a twin or a quarantine record) are vacuumed; other directories under the data directory (such as the Python launcher's VMs) are never touched.
* While a vacuum runs, `start`, `stop` and another `vacuum_vm` for that VM are refused (`runtime.vm.vacuuming`).
* A vacuum that fails after its twin was stopped spawns the twin again (unless quarantined), so the VM stays addressable.
* Directories are removed with `remove_dir_all`, which removes symlinks inside the guest-writable tree without following them.

A stream is retired by a **tombstone**, not deleted: the journal records that the stream ended, and a retired stream is neither replayed nor listed in the registry. The history stays in the journal.

=== Tombstones

[source,sql]
----
CREATE TABLE tombstones (
  persistence_id TEXT PRIMARY KEY,
  through        INTEGER NOT NULL,   -- events at or below are retired
  at             INTEGER NOT NULL
) STRICT;                            -- journal schema version 2; version 1 migrates in place
----

* `JournalMessage::Retire { id }` sets `through` to the stream's last position (answered `Retired` or `RetireFailed`). Retiring an empty or already retired stream changes nothing.
* A replay returns `Replay { events, last }`: the events above `through`, and the stream's last position with retired events included. A persistent actor appends after `last`, as an Akka persistent actor continues after its highest sequence number once its messages are deleted.
* A stream is listed only while it has an event above its tombstone.
* A name is reused by continuing its stream: a new twin for a vacuumed name replays nothing, so it is a fresh VM (`Created` with a new incarnation), and its events follow the tombstone. The writer fence is unchanged: an append must start at `last + 1`.

== Supervision

0002's framework choice is amended: VM-level supervision is a `MachineSupervisor` of our own over ractor's links and supervision events, with its restart policy as a pure function. `ractor-supervisor` is removed from the dependencies.

Why not `ractor-supervisor`'s `DynamicSupervisor`: its intensity counts all children together and its only outcome is a meltdown that fails the supervisor. Linked to Root, one VM failing repeatedly (an invalid configuration, say) would end the runtime; the restarted runtime spawns the same twin and melts down again, until systemd stops restarting it and every VM loses its control plane. No VM-level fault becomes healthy by restarting the runtime. It also gives the parent no restarted child's reference and fails on a first spawn error sent without a reply port.

=== Topology

----
Root ─┬─ Journal            linked, essential  ─┐
      ├─ Listener           linked, essential   ├─ any ends → Root fails → runtime exits → systemd restarts
      └─ MachineSupervisor  linked, essential  ─┘
           └─ VmTwin × name  linked to MachineSupervisor; one-for-one: VMs never affect each other
                └─ Builder, GuestVm, LocalQemu  linked to the twin; any ends → the twin fails
----

* Essential actors are systemic: their failure ends the runtime. Twins are not: a twin's failure never reaches past its own VM.
* The twin and its children are one restart unit (OTP's one-for-all, carried out by recovery): a child that ends makes the twin fail, and the restarted twin replays and reconciles (adopts a running machine, fails a start in progress, carries a stop on). Children are named after their twin (`…/builder`, `…/guest_vm`, `…/hypervisor`).
* Each persistent actor chooses per child whether its end is an observation or a reason to fail (`ChildPolicy`); the twin escalates for all three.

=== Per-VM lifecycle in the supervisor

----
 Spawning ──spawned──▶ Up ──failed, budget left──▶ Restarting{attempt, reason} ──backoff──▶ Spawning
    │ spawn error counts as a failure                │ budget exhausted
    └────────────────────────────────────────────────┴──▶ Quarantined{SuspiciousHalt} (persisted)
 Up ── stopped normally (vacuum) ─▶ removed
 Up ── Unrecoverable (twin alive, refusing) ─▶ Quarantined{Unreplayable}, as before
----

* Budget: 5 restarts within 10 minutes per VM; backoff 1 s, doubling, at most 30 s. The first failure restarts; quarantine comes only once the budget is spent.
* Twins fail with a typed failure, downcast by the supervisor; anything that doesn't downcast (a panic, an unknown error) is a bug. Reactions start as: persist conflict restarts at once without backoff; persist timeout, replay store error, an escalated child, a spawn failure and a bug restart after backoff. All count against the budget. Per-cause budgets and per-VM policy are room for later, inside the supervisor.
* Quarantine records carry a cause: `Unreplayable` (only `vacuum_vm` removes it) or `SuspiciousHalt` (the restart budget is spent; the record keeps the restart count and the last failures). Nothing touches the world when a twin fails, so processes, journal and logs stay for debugging. `amoeboid release_vm NAME` (`VmRequest::Release`, answered `VmReply::Released`) lifts a `SuspiciousHalt` quarantine: a tombstone on the record, a fresh budget, the twin spawned again. Releasing an `Unreplayable` quarantine is refused (`runtime.vm.not_releasable`) with a hint to vacuum; releasing a VM that isn't quarantined is `runtime.vm.not_quarantined`. Quarantine records are version 2 (`{"quarantined": {"cause": …}}`); version 1 records read as `Unreplayable`.

=== Requests by state

[cols="1,2,2"]
|===
|Twin state |`start`, `stop` |`status`
|Spawning |held per VM until up |held
|Up |to the twin |to the twin
|Restarting |refused at once (`runtime.vm.restarting`, hint: see `amoeboid status`) |Root answers `Restarting { reason, attempt }`
|Quarantined |refused |Root answers `Quarantined { cause, reason }`
|===

When a twin fails, Root answers every operation waiting on it with the failure (`runtime.vm.twin_failed`). Root learns a twin's reference from the supervisor (`Up`), so it never awaits a spawn in its own handler; a status question waits for twins being spawned and asks them once up.

Root's children (Journal, Listener, MachineSupervisor) are all essential, so its supervision handler has nothing to tell apart: any end ends the runtime. Which twin end is expected (a terminate) is known only to the supervisor, which owns the link.

Implementation notes:

* A failed twin's children are killed asynchronously and may still hold their registry names when it is respawned, so children are named `<twin>/<role>@<twin actor id>`. The twin's own name is freed before its supervisor hears of the end (ractor unregisters on `Stopping`), so a restart at once can't collide.
* A vacuum terminates the twin through the supervisor; a twin that is up stops the VM gracefully first. A twin that fails while the vacuum waits for its stop is terminated instead.
* The twin's error for a start interrupted by a restart now reads "the VM's twin restarted while the VM was starting" (`vm.restarted_while_starting`): it applies to a runtime restart and to a supervisor restart alike.

== Runtime placement

=== The runtime's own files

`daemon.lock` and `journal.sqlite` move to `$XDG_STATE_HOME/amoeboid`, apart from VM data in `$XDG_DATA_HOME/amoeboid`. This answers 0002's open question. The move is not implemented yet; until then both stay in `$XDG_DATA_HOME/amoeboid`, marked by a TODO in `runtime/paths.rs`.

=== systemd units

`amoeboid daemon install` writes `~/.config/systemd/user/amoeboid.socket` and `amoeboid.service` and enables the socket:

[cols="1,2"]
|===
|Setting |Reason
|`ListenStream=%t/amoeboid/runtime.sock`, `SocketMode=0600`, `DirectoryMode=0700` |same-user socket (0002, protocol)
|`Restart=on-failure` |a dead runtime comes back and adopts its VMs
|`KillMode=process` |VM processes already run in their own scopes; this spares them a second time
|`Environment="PATH=…"` captured at install |the user manager's `PATH` is often minimal; the runtime needs `nix`, `ssh-keygen` and `systemd-run`
|`ExecStart=` the `amoeboid-daemon` next to the `amoeboid` binary that ran `install` |the CLI and the runtime ship together and must match in protocol version
|===
